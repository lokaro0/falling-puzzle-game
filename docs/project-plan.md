# Falling Puzzle Game GUI版 開発計画

## 背景と目的

現在のFalling Puzzle Gameは、C++17とncursesで動作する1人用の落ちものパズルゲームである。実行にLinuxまたはWSLとncursesが必要なため、開発環境を持たない利用者が遊びにくい。

既存のゲームロジックと自動テストを生かし、Windowsで容易に起動できる2D GUIゲームへ移行する。起動、プレイ、結果確認、再挑戦までを一続きに体験できる状態を目指す。

## 現状

### 利用できるもの

- 盤面、ピース、移動、回転、消去、重力、Game Overのゲームロジック
- Next、スコア、ハイスコアの表示
- 消去点滅と1行ずつの重力表示
- ハイスコアのファイル保存
- domain、UI、storageの分離
- ゲームロジックと保存処理の自動テスト
- CMakeとGitHub Actionsによるビルド・テスト

### GUI移行前に把握している課題

- スコアは消去個数の累計であり、連鎖段数を保持していない
- `erased_group_count`は連結グループ数であり、連鎖段数ではない
- 消去と重力の演出中は待機処理によって通常のゲームループが止まる
- CMakeは常にncursesを要求するため、GUI版だけを独立してビルドできない
- タイトル画面、結果画面、Retryがない
- ハイスコアの保存先が実行時の相対パスになっている

現在の構成と過去の改善内容の詳細は、[アーキテクチャ資料](architecture.md)と[リファクタリング記録](refactoring-plan.md)を参照する。

## プロダクトの方針

連鎖を組むことで、表示、音、得点が段階的に盛り上がる落ちものパズルゲームを目指す。

最小GUI版ではncurses版の現在の仕様を初期基準とする。盤面、Next、スコア、ハイスコアの表示と既存の基本操作を維持し、連鎖、得点、演出などの意図的な変更は別の変更単位で実施する。

## 最初の正式版の完成条件

以下は目標とする完成形。11/7までの必須範囲と延期項目、日程は[基本設計と実装タスク](gui-implementation.md)に従う。

- Windows 11で、配布物からターミナルを操作せずに起動できる
- タイトル画面からゲームを開始できる
- Game Over後に結果を確認し、Retryまたはタイトルへ戻れる
- 同時消去と連鎖段数を区別して得点を計算できる
- 連鎖を画面表示と音で認識できる
- 既存の自動テストと、新しく追加する連鎖・得点・リセットのテストが成功する
- 開発環境を導入していない別のWindows PCで起動と基本プレイを確認できる
- 5人以上に説明なしで遊んでもらい、発見した問題と改善結果を記録する

## 対象範囲

- Windows向けGUI表示とキーボード入力
- タイトル画面とHigh Score・Tutorialの選択肢（当面は仮画面）
- プレイ画面
- Game Over後の結果画面
- Retryとタイトルへの復帰
- 連鎖段数、得点、最大連鎖数
- 消去、連鎖、着地、Game Overの基本的な演出と効果音
- ハイスコアの保存
- Windows向け配布物
- 自動テスト、手動テスト、配布テスト、ユーザーテスト

## 対象外

- リアルタイムオンライン対戦
- マッチングとルーム管理
- ユーザーアカウント
- スマートフォン版
- ゲームパッド対応
- ステージ制、ストーリーモード、対戦AI

## 基本機能の完成後に検討するもの

- Web版
- オンラインランキング

これらは最初の正式版の完成条件には含めない。基本機能と配布テストが完了し、開発期間に余裕がある場合に実施を判断する。

## 技術上の前提

- C++17とCMakeを継続して使用する
- GUIライブラリはraylibを採用する（[選定記録](decisions/001-gui-library.md)）
- domain層をGUIライブラリ、音声、ファイル保存へ直接依存させない
- 既存のdomain層、storage層、自動テストを可能な限り再利用する
- GUI版では、待機処理ではなく状態と経過時間によって演出を進める
- 第三者の画像、フォント、音声を使用する場合は利用条件と出典を記録する

## 開発の進め方

1. 機能要件、非機能要件、受け入れ条件を定義する
2. GUIライブラリでウィンドウ、描画、入力、音声、CMake連携を検証する
3. 技術選定の理由をADRへ記録する
4. 現行仕様を基準に最小GUI版を作成する
5. タイトル、結果画面、Retryを追加し、Windows向け配布を確認する
6. 連鎖、得点、演出、効果音を追加する
7. 通しプレイと配布確認を行い、重要な問題を修正する。本格的な外部テストと改善は後回しにする
8. Releaseビルド、配布物、README、テスト結果を整理して正式版を作成する

変更は機能ごとに小さく分け、各段階でビルド、自動テスト、必要な手動確認を行う。
